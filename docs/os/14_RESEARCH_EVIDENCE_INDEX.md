## 1. PURPOSE

Preserve the provenance of the World-Class Website OS while keeping raw research out of normal operating context.

This file answers:

> What evidence supports this rule or conclusion -> what kind of evidence is it -> where did it come from -> how strong is it -> when should it be retrieved -> what may it legitimately change?

File 14 is the retrieval map between the operating system and the cold evidence archive. It does not attempt to make ordinary builds carry their own literature review.

## 2. AUTHORITY BOUNDARY

Authority remains:

`A0 Project Brief -> A1 Project Custom Instructions -> A2 Governing Doctrine -> A3 Strategy Vector + Specialist Systems -> A4 Scorecard / QA -> A5 Pattern / Anti-Pattern Libraries -> A6 Research / Evidence`

A6 is foundational evidence, not day-to-day command authority.

Evidence can:
- explain why a rule exists;
- challenge an overbroad rule;
- expose an outdated standard;
- support a specialist/pattern update;
- support a doctrine-change proposal;
- preserve provenance for future maintainers.

Evidence cannot, by itself:
- override project purpose;
- waive a hard integrity obligation;
- promote a fashionable technique into doctrine;
- replace causal reasoning with precedent;
- silently rewrite an upstream module.

## 3. OPERATING PREMISE

The system distinguishes:

`Law -> Rule -> Pattern -> Example -> Evidence`

Research moves upward only through validation:

`Evidence -> Observation / Finding -> Synthesis -> Candidate Rule -> Adversarial Validation -> Doctrine / Specialist Rule / Pattern`

Reject:

`Prestigious Example -> Universal Rule`

A cool implementation is an observation. Repetition may support a pattern. Only sufficiently validated causal mechanisms can justify stronger system rules.

## 7. EVIDENCE TAXONOMY — AUTHORITATIVE

Preserve the File 01 evidence taxonomy.

### OBSERVED
Directly encountered, inspected, reproduced, or measured.

Can support:
- what happened;
- what a site/interface actually did in the observed context;
- measured behavior/performance/state;
- direct QA/forensic findings.

Cannot alone support:
- why it happened;
- broad causal generalization;
- effectiveness across other contexts;
- doctrine.

### DOCUMENTED
Explicitly supported by a credible primary or authoritative source.

Can support:
- standards requirements;
- documented platform/browser behavior;
- official product behavior;
- stated design/technical rationale where source is competent to make it.

Cannot automatically support:
- independent effectiveness;
- universality outside the documented scope;
- marketing claims as objective outcomes.

### INFERRED [HIGH / MEDIUM / LOW]
A conclusion not directly documented but supported by available evidence.

**HIGH:** multiple converging observations/sources, strong causal fit, meaningful counterexample review.  
**MEDIUM:** plausible mechanism with material supporting evidence but incomplete validation.  
**LOW:** weakly supported interpretation, analogy, or limited sample.

Inference must remain labeled as inference.

### HYPOTHESIZED
A plausible explanation or candidate relationship requiring validation.

Hypotheses belong in research/prototyping, not as unqualified operating rules.

## 8. OBSERVATION / INTERPRETATION / GENERALIZATION

Forensic work separates three layers:

```text
OBSERVATION:
What was directly seen/measured.

INTERPRETATION:
What mechanism may explain it.

GENERALIZATION:
What broader rule, if any, the evidence may support.
```

Never collapse these layers.

Example:
- Observation: a site changes a persistent desktop index into an on-demand mobile index.
- Interpretation: the persistent desktop geometry is less important than preserving orientation/access.
- Generalization: this may support G5 when corroborated across contexts.

## 9. SOURCE-TYPE REGISTRY

Use these source types when material:

- `LIVE_SITE_OBSERVATION` — direct inspection of a live experience;
- `PRIMARY_DOCUMENTATION` — official product/design/technical source;
- `STANDARD` — normative or authoritative standards source;
- `PEER_REVIEWED_RESEARCH` — scholarly empirical/theoretical work;
- `AUTHORITATIVE_GUIDANCE` — credible institutional HCI/accessibility/technical guidance;
- `TECHNICAL_DOCUMENTATION` — browser/platform/framework/library documentation;
- `BENCHMARK_MEASUREMENT` — measured performance/technical result;
- `USER_RESEARCH` — task/user evidence;
- `EXPERT_SECONDARY` — specialist interpretation not itself primary evidence;
- `INTERNAL_SYNTHESIS` — cross-source mechanism analysis;
- `COUNTEREXAMPLE` — evidence intentionally testing universality;
- `QA_FIELD_SIGNAL` — repeated File 13 finding or post-launch observation;
- `HYPOTHESIS` — unvalidated candidate explanation.

Source type and evidence class are related but not identical. An authoritative standard is DOCUMENTED; a direct forensic observation is OBSERVED; an internal synthesis is usually INFERRED.

## 10. SOURCE WEIGHT IS QUESTION-SPECIFIC

No universal source ranking settles every question.

Prefer evidence capable of answering the actual claim.

Examples:
- WCAG conformance question -> current W3C normative documentation outranks a design blog.
- Current browser API behavior -> current browser/platform documentation plus direct testing.
- Whether a motion pattern exists -> direct live-site observation.
- Whether it improves comprehension -> user/task evidence outranks aesthetic precedent.
- Whether a hotel site creates a sense of place -> project/user evidence plus relevant precedent; a generic commerce heuristic may be contextually incomplete.

## 14. PROVENANCE MINIMUM

A material evidence item must preserve enough information to answer:
1. What exactly was observed/documented?
2. Where did it come from?
3. When/version?
4. What context/task/population applies?
5. Is the causal meaning observed or inferred?
6. What claim does it support or challenge?
7. What are the limitations?
8. Can someone retrieve/reproduce it?
9. Has newer evidence superseded it?

Orphan evidence cannot support a doctrine change.

## 15. RESEARCH QUALITY DIMENSIONS

Evaluate evidence through:
- directness;
- source competence/authority;
- measurement quality;
- context match;
- replication across contexts;
- causal plausibility;
- counterevidence;
- recency/version fit where relevant;
- independence from commercial/self-promotional incentive;
- reproducibility/retrievability.

Use qualitative judgment rather than fabricated confidence percentages.

## 16. CONFIDENCE

### HIGH
Evidence is direct/high-quality, materially replicated or strongly convergent, contextually relevant, and important counterevidence has been considered.

### MEDIUM
Evidence is credible and causally plausible but limited in replication, scope, measurement, or context transfer.

### LOW
Evidence relies mainly on analogy, limited observation, preference, untested interpretation, or weak/indirect sources.

Confidence is not severity, authority, or importance.

## 17. EVIDENCE COMBINATION

Strong conclusions often combine:
- direct observation;
- authoritative documentation;
- cross-site replication;
- external HCI/accessibility evidence;
- counterexamples;
- causal synthesis.

Do not count sources as votes. Five derivative blog posts do not outweigh one current normative standard on a standards question.

## 18. COUNTEREXAMPLES ARE FIRST-CLASS EVIDENCE

Use counterexamples to test whether:
- a supposed law is falsely universal;
- a common pattern is merely common;
- opposite techniques can succeed in different Strategy Vectors;
- the inferred causal mechanism is wrong;
- scope/conditions need refinement.

One valid counterexample can disprove a universal claim. It does not prove the opposite universal claim.

## 19. EVIDENCE CONFLICT STATES

Possible outcomes:
- `RESOLVED — SUPPORTS CURRENT POSITION`
- `RESOLVED — CURRENT POSITION REQUIRES REFINEMENT`
- `RESOLVED — CURRENT POSITION SHOULD CHANGE`
- `CONTEXT-DEPENDENT — BOTH VALID UNDER DIFFERENT CONDITIONS`
- `UNRESOLVED EVIDENCE CONFLICT`

Uncertainty is a valid result.

## 20. CONFLICT-RESOLUTION PROCESS

When credible evidence conflicts:
1. confirm both address the same claim;
2. compare project/archetype/population/task;
3. compare source type and competence;
4. compare recency/version;
5. separate observation from interpretation;
6. inspect measurement differences;
7. identify hidden variables;
8. seek counterexamples;
9. preserve residual uncertainty;
10. route only the justified change.

Do not force consensus because the OS would look tidier.

- File 08 continuous-integrity requirement;
- File 09 early-risk validation.

Workflow is primarily a synthesis of existing authority relationships, not an independent design doctrine.

## 57. SPECIALIST EVIDENCE MAP — FILE 13

**Scorecard / QA / Red Team**  
Evidence families:
- specialist acceptance gates;
- File 08 hard integrity;
- rendered/functional QA requirements;
- severity/evidence-confidence separation;
- adversarial validation logic;
- production feedback.

Repeated findings may create research questions; isolated project defects do not automatically modify the OS.

## 58. DOCTRINE VALIDATION TRIGGERS

Require evidence review when:
- a governing law is challenged;
- credible evidence contradicts a law or its stated scope;
- a repeated observation appears inconsistent with doctrine;
- a specialist rule has become suspiciously universal;
- a pattern is proposed for promotion into doctrine;
- technology/standards change a material integrity assumption;
- repeated File 13 failures suggest current guidance may be systematically insufficient;
- a formal doctrine change is proposed.

## 59. DOCTRINE CHANGE THRESHOLD

A governing law changes only when:
1. meaningful new evidence challenges or materially improves it;
2. provenance is adequate;
3. counterexamples are actively sought;
4. causal reasoning is reconsidered;
5. alternate explanations are addressed;
6. scope/archetype effects are analyzed;
7. downstream module impact is assessed;
8. the proposal survives adversarial validation;
9. File 99 records the version/change/migration.

Doctrine should be difficult, not impossible, to change.

## 61. CHANGE DESTINATION

Research can resolve to:
- `NO CHANGE`;
- `DOCUMENTATION CLARIFICATION`;
- `SPECIALIST RULE REFINEMENT`;
- `PATTERN LIBRARY UPDATE`;
- `ANTI-PATTERN UPDATE`;
- `INTEGRITY/STANDARDS UPDATE`;
- `DOCTRINE CHANGE PROPOSAL`;
- `NEW RESEARCH REQUIRED`.

Choose the lowest authority layer that correctly owns the change.

## 62. SPECIALIST-RULE CHANGE STANDARD

A specialist rule may change with credible context-specific evidence when:
- governing doctrine remains intact;
- changed conditions/scope are explicit;
- downstream impact is understood;
- relevant counterexamples are considered;
- the owning module is versioned through File 99.

Threshold is lower than doctrine because specialist rules are context-sensitive.

## 63. PATTERN CHANGE STANDARD

Patterns are the fastest-changing layer.

Update File 10 when:
- a new useful implementation family appears;
- an existing pattern's fit/rejection conditions change;
- risks/costs change materially;
- a pattern becomes obsolete;
- new evidence reveals a better substitute.

Popularity alone is not enough.

## 64. ANTI-PATTERN CHANGE STANDARD

Update File 11 when a recurring failure mechanism is shown to be:
- genuinely systemic rather than stylistic dislike;
- causally diagnosable;
- meaningfully distinct from existing failures;
- useful for routing correction.

Do not add an anti-pattern every time one bad site is seen.

## 65. FILE 13 -> FILE 14 FEEDBACK LOOP

```text
Repeated QA finding
-> determine project-specific vs systemic
-> inspect existing OS guidance
-> formulate exact research question if guidance may be insufficient
-> inspect File 14 index
-> retrieve minimum evidence
-> conduct bounded new research only if needed
-> evaluate OS change destination
-> update owning module + File 99 if justified
```

One failed build is not a research program.

## 66. NEW RESEARCH PROTOCOL

When genuine new research is required:
1. define the exact unresolved claim;
2. define what evidence would change the decision;
3. inspect existing archive first;
4. identify the evidence gap;
5. seek primary/authoritative evidence where possible;
6. inspect relevant live behavior directly where needed;
7. include counterexamples;
8. label OBSERVED / DOCUMENTED / INFERRED / HYPOTHESIZED;
9. distinguish context-specific results from generalization;
10. synthesize cautiously;
11. update File 14 provenance;
12. route justified OS changes through File 99.

## 67. STOP RULE FOR RESEARCH

Stop when:
- the consequential uncertainty is sufficiently reduced;
- more desk research is unlikely to alter the decision;
- the next useful evidence is a prototype, task test, production measurement, or user study;
- evidence conflict is honestly unresolved and further retrieval has diminishing return.

More sources are not automatically more truth.

## 68. RESEARCH RED FLAGS

Flag:
- prestige bias;
- Awwwards bias;
- survivorship bias;
- cherry-picking;
- confirmation bias;
- novelty bias;
- recency bias;
- category/archetype mismatch;
- screenshots without interaction context;
- correlation presented as causation;
- implementation frequency presented as effectiveness;
- primary/secondary source confusion;
- outdated technical guidance;
- marketing claims treated as independent outcome evidence;
- fabricated metrics;
- invented filenames or provenance;
- absent counterevidence for consequential claims.

## 69. ARCHETYPE TRANSFER CAUTION

Before generalizing evidence across archetypes, ask:
- Is the primary job similar?
- Is buyer/action commitment similar?
- Is information complexity similar?
- Is experiential intensity similar?
- Is interaction novelty similar?
- Is trust burden similar?
- Does the same failure/benefit mechanism plausibly operate?

Examples:
- luxury pacing does not automatically fit public-service task completion;
- ecommerce navigation evidence may not settle immersive cultural exploration;
- documentation density is not a campaign default;
- spatial portfolio interaction is not a checkout precedent.

## 70. BENCHMARK PRESTIGE CAUTION

Inclusion in the 36-site universe means:
- the site was considered useful to study.

It does **not** mean:
- the site is perfect;
- all its techniques are approved;
- it converts better;
- it is accessible;
- its implementation transfers to another archetype;
- prestige establishes causation.

## 71. RESEARCH-TO-PATTERN RULE

Observed implementation may suggest a pattern.

Before File 10 adoption require:
- named job;
- Strategy Vector/context fit;
- known risks;
- responsive/accessibility/performance implications;
- evidence limitations;
- File 09 review when complexity is material.

## 72. RESEARCH-TO-ANTI-PATTERN RULE

Observed failure may suggest an anti-pattern only when:
- the root cause is identified;
- the failure mechanism recurs or is sufficiently consequential;
- it is not merely aesthetic preference;
- false-positive conditions are understood;
- File 11 can route a correction.

## 73. PROJECT_WEBSITE_SPEC RELATIONSHIP

Do not put the research archive into project specs.

Write evidence into `PROJECT_WEBSITE_SPEC` only when it materially affects:
- a project-specific exception;
- a disputed requirement;
- a high-impact unresolved assumption;
- a current standards-sensitive decision;
- an evidence-backed deviation from normal OS guidance;
- an accepted residual risk.

Use a compact pointer, not the whole research brief.

## 74. RELATIONSHIP TO FILE 01

File 01 owns the laws.

File 14 owns retrievable evidence/provenance supporting or challenging them.

A doctrine change is implemented in File 01 only after File 14 evidence review and adversarial validation, then registered in File 99.

## 75. RELATIONSHIP TO FILE 08

File 08 owns current operational integrity rules.

File 14 preserves/locates evidence and reminds the system to re-check current authoritative standards for volatile requirements.

Do not make developers open the research archive to learn how to label a form.

## 76. RELATIONSHIP TO FILE 09

File 09 owns project-level complexity decisions and uses the least expensive evidence capable of reducing uncertainty.

File 14 is needed only when a broader causal claim, precedent interpretation, or OS-level complexity rule requires evidence review.

## 77. RELATIONSHIP TO FILE 13

File 13 owns acceptance.

File 14 does not overturn a reproducible QA failure because a case study looks good. It may be invoked if the requirement itself is disputed or if repeated QA outcomes suggest an OS revision.

## 78. RELATIONSHIP TO FILE 99

File 14 answers:

> Why should the system change, and what evidence supports it?

File 99 answers:

> What changed, from which version to which version, when, and what reconciliation/migration is required?

File 14 never substitutes for version history.

## 79. CHANGE-CONTROL SEQUENCE

When evidence justifies an OS change:

`Evidence question -> File 14 retrieval/research -> proposed change + impact -> adversarial validation -> update owning module -> update dependent modules if needed -> File 99 version/changelog -> File 14 provenance pointer update -> reconciliation QA`

Do not let File 14 directly mutate the operating system in secret.

## 80. DEPRECATED / REJECTED HYPOTHESES

File 14 should preserve meaningful rejected research ideas when future maintainers are likely to repeat them.

Record:

```text
HYPOTHESIS:
STATUS: REJECTED / SUPERSEDED / NARROWED
WHY:
EVIDENCE:
REPLACED BY:
DATE / VERSION:
```

Do not preserve every abandoned thought. Preserve recurring traps.

## 81. V1 DEPRECATED UNIVERSALIZATIONS

The v1 research explicitly rejects promoting these into universal quality laws:
- premium = minimalism;
- premium = whitespace;
- premium = giant serif typography;
- asymmetry = sophistication;
- motion = sophistication;
- WebGL/3D = world-class;
- mobile = shrunken desktop;
- one landing-page/funnel structure fits all;
- high Lighthouse score = overall site quality.

These techniques/metrics remain usable under conditions owned by the specialist modules.

## 82. UNRESOLVED RESEARCH QUESTIONS

Keep only material unresolved questions.

### URQ-001 — Raw archive registration
Exact v1 raw research filenames and complete 36-/12-site rosters are not surfaced in the accessible Library index. Register them when the archive is migrated or made retrievable; do not rerun research to recreate names from memory.

### URQ-002 — Standards freshness
Version-sensitive standards require current-source verification at use time. This is operational, not evidence that doctrine is unstable.

Add future questions only when they could materially change the OS.

## 83. ARCHIVE REGISTRATION PROTOCOL

When exact raw files become available:
1. list exact filename/path;
2. assign archive role;
3. preserve created/reviewed date if available;
4. map to evidence family / IDs;
5. record which laws/modules it supports/challenges;
6. mark superseded duplicates;
7. update File 14 pointer only;
8. record structural archive migration in File 99 if meaningful.

Do not alter doctrine merely because provenance became better organized.

## 84. TOKEN / CONTEXT EFFICIENCY

Rules:
- index first;
- claim-specific retrieval;
- retrieve evidence families, not the corpus;
- prefer archive pointers over copied passages;
- use compact evidence briefs;
- do not re-prove doctrine during normal builds;
- do not load File 14 merely because a specialist rule cites evidence;
- stop research when the decision is sufficiently resolved.

File 14 succeeds partly by staying closed.

## 85. RESEARCH REQUEST ROUTER

Classify a request:

**WHY / PROVENANCE** -> File 14 R0/R1.  
**CONTRADICTORY EVIDENCE** -> R2.  
**DOCTRINE CHANGE** -> R2 + doctrine evidence packet.  
**CURRENT STANDARD** -> current authoritative source + File 14 update if material.  
**NEW OPEN QUESTION** -> inspect archive, then R3 only if gap remains.  
**ORDINARY BUILD** -> do not load File 14.

## 86. EVIDENCE BRIEF SUCCESS STANDARD

A useful brief should state:
- exact question;
- current OS position;
- evidence actually retrieved;
- supporting and challenging evidence;
- context/limitations;
- confidence;
- practical implication;
- whether any OS change is justified;
- owning route.

Anything longer should earn its length.

## 87. FILE 14 ACCEPTANCE GATE

PASS only when File 14:
- preserves A6 authority and cannot override higher layers by precedent;
- preserves OBSERVED / DOCUMENTED / INFERRED / HYPOTHESIZED;
- indexes rather than duplicates raw research;
- records the confirmed v1 research history;
- transparently identifies unavailable exact archive filenames instead of inventing them;
- maps G1–G7 to retrievable evidence families;
- indexes specialist evidence families;
- defines provenance and source types;
- separates observation / interpretation / generalization;
- treats counterexamples as first-class evidence;
- resolves or preserves credible evidence conflict appropriately;
- defines qualitative confidence;
- handles freshness/version sensitivity;
- requires current standards verification when material;
- defines cold-context and minimum-sufficient retrieval;
- defines doctrine/specialist/pattern/anti-pattern change paths;
- links repeated File 13 findings to research only when systemic;
- defines new research and stop rules;
- defines relationship to File 99;
- protects `PROJECT_WEBSITE_SPEC` from research bloat;
- remains token-efficient.

## 88. INTERNAL RED TEAM — ARCHIVE DUPLICATION

Ask:
- Did File 14 start reproducing raw forensic reports?
- Could the same function be served by a pointer?
- Is the index becoming larger than the useful archive slice it indexes?

If yes, compress.

## 89. INTERNAL RED TEAM — PRESTIGE / AWARDS BIAS

Ask:
- Does a famous/awarded site receive causal authority merely for being famous?
- Are we studying what exists or assuming what works?
- Is commercial/design prestige being mistaken for task success, accessibility, or conversion?

Prestige is sampling context, not proof.

## 90. INTERNAL RED TEAM — EVIDENCE CLASS CONFUSION

Ask:
- Was an inference labeled observation?
- Was first-party marketing labeled independent validation?
- Was a synthesis mislabeled documented?
- Was a hypothesis promoted into a rule?

Correct the label before reasoning further.

## 91. INTERNAL RED TEAM — CAUSAL CONFUSION

Ask:
- Are correlated design choices being called causes?
- Is frequency being treated as effectiveness?
- Did we account for brand, audience, content, acquisition, product, or execution quality?

Avoid conversion theater from screenshots.

## 92. INTERNAL RED TEAM — COUNTEREXAMPLES

Ask:
- Did we actively seek disconfirming evidence?
- Did one counterexample narrow an overbroad claim rather than trigger the opposite universal?
- Are archetype differences explaining apparent conflict?

## 93. INTERNAL RED TEAM — DOCTRINE CHANGE RATE

Two failure modes:
- doctrine changes whenever trends change;
- doctrine becomes sacred despite strong contradictory evidence.

Require high-quality provenance + adversarial validation + downstream-impact analysis.

## 94. INTERNAL RED TEAM — FRESHNESS

Ask:
- Is standards/tool/browser/live-site evidence stale?
- Are dates/versions material to the claim?
- Are we treating an old implementation as current behavior?

Revalidate F1/F2 evidence when needed.

## 95. INTERNAL RED TEAM — INVENTED PROVENANCE

Ask:
- Did we invent a filename, evidence ID, source date, roster member, or quote because the archive was incomplete?

If yes, remove it and record the provenance gap.

ARG-001 exists specifically to prevent this failure.

## 96. INTERNAL RED TEAM — CONTEXT TRANSFER

Ask:
- Are we generalizing evidence across project archetypes without matching job/complexity/commitment/experience/trust?
- Are luxury, commerce, public-service, editorial, and experience-first evidence being treated as interchangeable?

Require context-fit reasoning.

## 97. INTERNAL RED TEAM — RESEARCH REOPENING

Ask:
- Is a current decision actually blocked by missing evidence?
- Could current doctrine/specialist guidance answer it?
- Are we browsing because uncertainty is consequential or because browsing feels responsible?

The research phase is closed by default.

## 98. INTERNAL RED TEAM — ID BUREAUCRACY

Ask:
- Does an ID improve retrieval?
- Does the underlying item actually exist?
- Are we spending more effort maintaining taxonomy than learning from evidence?

Use IDs selectively.

## 99. INTERNAL RED TEAM — TOKEN BLOAT

Ask:
- Can a pointer replace prose?
- Can an evidence family replace a long source list?
- Is the full archive being loaded for a claim one source can answer?

Evidence rigor and context efficiency are allies.

## 100. FILE 14 WORKFLOW

`Evidence/provenance question -> classify trigger -> File 14 index -> choose R0/R1/R2/R3 -> retrieve minimum evidence -> separate observation/documentation/inference/hypothesis -> inspect context/counterevidence/freshness -> resolve confidence/conflict -> decide change destination -> if change, update owning module -> File 99 -> update provenance pointer -> return archive cold`

## 101. HANDOFF TO FILE 99

Provide File 99 with:
- current OS version target `1.0.0`;
- module version/status for File 14;
- confirmed authority role A6;
- completed module registry through File 14;
- known research-state statement: v1 research closed;
- standards/freshness behavior that can trigger future module revisions;
- doctrine-change threshold/history requirements;
- specialist/pattern/anti-pattern change categories;
- evidence provenance relation: File 14 explains **why** a change is justified; File 99 records **what/version/migration** changed;
- unresolved archive-registration item `ARG-001` / `URQ-001` as a provenance-maintenance issue, not a reason to reopen research;
- requirement that whole-system red-team occurs after File 99 construction and before v1.0.0 release reconciliation.

## 102. SUCCESS STANDARD

File 14 succeeds when the OS can remain evidence-backed without dragging its entire research history into ordinary work; when a future maintainer can distinguish observation from interpretation, retrieve evidence for G1–G7 and specialist systems, challenge doctrine without trend-chasing, preserve unresolved conflicts honestly, revalidate changing standards, and route justified changes through explicit version control rather than silent drift.
