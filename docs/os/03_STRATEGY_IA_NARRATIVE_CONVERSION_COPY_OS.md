## 1. PURPOSE

This module determines what the website must communicate, to whom, in what structure, in what order, with what evidence, and toward what decision or action.

It governs audience/job framing, value proposition architecture, information architecture, taxonomy/navigation, user journeys, page roles, narrative sequence, attention sequence, progressive disclosure, proof, trust, objections, buyer readiness, conversion architecture, CTA logic, section architecture, copy hierarchy, and content priority.

It does not decide fonts, grids, color, spacing, crop, animation, breakpoints, CSS, or frameworks.

## 2. OPERATING PREMISE

A website is a structured decision environment. At any moment a user may need to know:
1. Where am I?
2. Is this relevant?
3. What is offered?
4. Why care?
5. How does it work?
6. Is it credible?
7. Does it fit my situation?
8. What does it cost in money, effort, risk, or attention?
9. What should I do next?

Architecture should make the next important answer easier to obtain.

Do not force every project into one funnel. Users may arrive cold, category-aware, offer-aware, comparing, returning, or action-ready.

## 3. REQUIRED INPUTS

Before substantial work, obtain or provisionally infer:
- Website Strategy Vector
- primary/secondary audience
- primary user job
- business/site objective
- primary action
- buyer/action commitment
- information complexity
- trust burden
- awareness state where known
- offer/product/service structure
- available proof
- meaningful differentiation
- constraints
- content inventory for redesigns
- known entry sources when relevant

Do not invent customer pain, objections, outcomes, proof, competitors, guarantees, pricing, or testimonials.

## 4. CORE STRATEGY MODEL

Resolve six questions.

### STRAT-1 — WHO?
Capture role/situation, current problem/task, prior knowledge, decision authority, motivation, constraints, uncertainty, and stakes.

### STRAT-2 — JOB
Use:
`When [situation], the user needs to [job], so they can [desired progress/outcome].`

### STRAT-3 — BUSINESS OBJECTIVE
Define an observable outcome: qualified demo, purchase, booking, understanding, signup, adoption, inquiry, etc. Avoid vague goals such as “look premium.”

### STRAT-4 — DECISION
What decision must the user be able to make?

### STRAT-5 — FRICTION
Classify:
- clarity
- relevance
- credibility
- value
- comparison
- risk
- effort
- cost
- timing
- action

### STRAT-6 — REQUIRED BELIEFS
List what must be reasonably believed before the intended action is appropriate.

## 6. VALUE PROPOSITION ARCHITECTURE

A value proposition is not merely a headline. Resolve:
- User Context
- Desired Outcome
- Offer
- Mechanism
- Difference
- Evidence
- Tradeoff

A qualified visitor should ultimately be able to answer:
- What is this?
- Is it relevant?
- What outcome does it enable?
- How?
- Why this approach?
- Why believe it?

Not all answers need to appear in the hero. They must arrive before the user is asked to make a decision requiring them.

### Failure modes
- category without value
- outcome without mechanism
- feature dump
- market-speak
- differentiation without relevance
- proofless superlative

Copy strength must not exceed evidence strength.

## 7. INFORMATION ARCHITECTURE

IA determines what content exists, how it is grouped, what is primary/secondary, how users find it, how categories are named, how deep the structure becomes, and which content belongs on which page.

Create four inventories:

### User Question Inventory
Questions users need answered.

### Content Inventory
Actual available content. Mark missing content rather than designing imaginary proof.

### Task Inventory
Learn, browse, compare, filter, evaluate, estimate, book, contact, buy, download, apply, use.

### Organizational Inventory
Internal concepts/product lines/departments used specifically to identify where company organization conflicts with user mental models.

## 8. IA GROUPING RULE

Prefer user-recognizable distinctions:
- task
- outcome
- product type
- workflow stage
- role
- problem
- destination
- use case
- topic

Avoid arbitrary organization by internal department, content format, clever branded vocabulary, or implementation technology unless the audience genuinely thinks that way.

## 9. CATEGORY VS FILTER VS ATTRIBUTE

Use a **category** for a meaningfully different scope.
Use a **filter** to narrow items that remain in a common scope.
Use an **attribute** to support comparison without requiring separate navigation.

Do not turn every difference into a branch.

## 10. IA DEPTH

Deeper is not automatically worse; shallow is not automatically better. Evaluate clarity per level, information scent, number/relationship of choices, backtracking risk, destination predictability, and orientation.

Do not hide critical information merely to make pages appear clean.

## 11. NAVIGATION ARCHITECTURE

Classify navigation as:
- GLOBAL
- LOCAL
- CONTEXTUAL
- UTILITY
- CONVERSION

Importance is not the same as global relevance.

### Information scent test
If the destination disappeared and the user saw only the label plus context, could they reasonably predict what they will get?

Grade: STRONG / ADEQUATE / WEAK / MISLEADING.

Avoid empty labels such as Explore, Discover, Learn, Solutions, Resources, More unless context makes destination unmistakable.

## 12. USER JOURNEYS

Model decision-relevant journeys rather than one imaginary linear funnel.

```text
ENTRY
→ CURRENT INTENT
→ REQUIRED INFORMATION
→ DECISION
→ ACTION
→ NEXT STATE
```

## 13. ENTRY STATES

- COLD
- CATEGORY-AWARE
- OFFER-AWARE
- COMPARISON
- RETURNING
- ACTION-READY

Do not force action-ready users through introductory theater or cold users into unexplained conversion.

## 14. PAGE ROLE

Each page gets one dominant role:
- ORIENT
- EXPLAIN
- EXPLORE
- COMPARE
- PROVE
- CONVERT
- TRANSACT
- SUPPORT
- USE

Record:
```text
PAGE:
PRIMARY ROLE:
PRIMARY USER:
ENTRY STATE:
QUESTION ANSWERED:
DECISION ENABLED:
PRIMARY NEXT STEP:
```

## 15. NARRATIVE ARCHITECTURE

Narrative is: **what must be understood before what?**

Build a Narrative Dependency Map for each required belief.

### Narrative modes

**UTILITY** — Need → Answer → Details → Action

**EVALUATION** — Relevance → Value → Mechanism → Evidence → Fit → Risk Resolution → Action

**COMPARISON** — Decision Criteria → Choices → Differences → Tradeoffs → Selection

**TRANSACTION** — Product/Offer → Fit → Decision Information → Confidence → Action

**NARRATIVE / EXPERIENCE** — Context → Atmosphere → Discovery → Meaning → Specific Offer/Info → Action

Modes are context-dependent, not universal templates.

## 16. ATTENTION ARCHITECTURE

Content-priority levels (`PRIORITY A1–A4`, distinct from AUTHORITY A0–A6):
- PRIORITY A1 — PRIMARY
- PRIORITY A2 — SUPPORTING
- PRIORITY A3 — OPTIONAL
- PRIORITY A4 — DEFERRED

For each section ask:
1. What single idea deserves first attention?
2. What is secondary?
3. What can be deferred?
4. What distracts?
5. What duplicates elsewhere?
6. What does the user know afterward that they did not know before?

## 17. SECTION CONTRACT

Every section requires:

```text
SECTION ID:
SECTION JOB:
USER QUESTION:
PRIMARY MESSAGE:
SUPPORTING MESSAGE:
REQUIRED PROOF:
PRIMARY ACTION:
INFORMATION PRIORITY:
PREVIOUS-SECTION DEPENDENCY:
NEXT-SECTION BRIDGE:
REMOVAL CONSEQUENCE:
```

Removal test: if removing a section loses no important belief, decision, orientation, proof, or action, remove or merge it.

## 18. SECTION ORDER

Order by causal dependency rather than familiar landing-page templates. Ask what doubt the previous claim creates and when proof/detail/action becomes relevant.

## 19. PROGRESSIVE DISCLOSURE

Use progressive disclosure to preserve attention while keeping depth available.

Primary layer: frequent/high-value/essential decision information.
Secondary layer: detail/specifications/advanced use cases/deep evidence/uncommon questions.

Do not hide critical pricing, restrictions, product differences, or required action information merely for visual cleanliness.

## 20. PROOF ARCHITECTURE

Proof exists to support a claim.

Create a Claim–Proof Matrix:

```text
CLAIM:
Importance:
Skepticism level:
Evidence required:
Evidence available:
Placement:
Gap:
```

### Proof types
- direct outcome
- scale
- customer
- authority
- product
- process
- social
- guarantee/risk reversal when real

Evaluate proof by specificity, relevance, verifiability, source independence, recency, similarity to target user, and directness.

Conditional rule: place material evidence near enough to the claim that it can resolve the doubt the claim creates.

If proof does not exist, reduce claim strength, identify the content requirement, use transparent mechanism/process evidence, mark provisional, or acquire evidence. Never fabricate stronger copy.

## 21. OBJECTION ARCHITECTURE

Create an Objection Register:

```text
OBJECTION:
Type:
Who has it:
When it appears:
Severity:
Answer:
Proof:
Placement:
```

Possible types: fit, trust, price, implementation, complexity, switching, capability, timing, risk, authority, support, compatibility, policy.

Answer objections when decision-relevant. Do not invent objections merely to populate an FAQ.

FAQ is for long-tail/procedural/secondary concerns, not unresolved primary architecture.

## 22. DECISION-STATE MODEL

- D0 ORIENT — What is this?
- D1 RELEVANCE — Is this connected to my situation?
- D2 VALUE — Is the outcome worth caring about?
- D3 UNDERSTANDING — How does it work?
- D4 CONFIDENCE — Can I believe this?
- D5 FIT — Does it fit my needs/constraints?
- D6 RISK RESOLUTION — What could stop me?
- D7 ACTION — Am I ready and what happens next?

Users may skip or revisit states. Architecture should support actual state rather than enforce ritual order.

## 23. BUYER/ACTION READINESS

**LOW COMMITMENT** — browse/read/download/free signup. CTA may appear immediately.

**MEDIUM COMMITMENT** — trial/account/purchase/booking. Requires relevant decision information and confidence.

**HIGH COMMITMENT** — enterprise demo/luxury inquiry/high-ticket service/application. Usually requires stronger relevance, evidence, risk reduction, and process clarity.

This is not a page-length formula.

## 24. CONVERSION ARCHITECTURE

Define:
- desired action
- who should take it
- when they are ready
- what must precede it
- alternatives
- what happens after

A conversion is successful when the right user can take the right next action with appropriate understanding.

### CTA taxonomy
- PRIMARY CTA
- SECONDARY CTA
- UTILITY ACTION

### CTA labels
Communicate destination/action. Prefer explicit labels such as View pricing, Request a demo, Check availability, Compare plans.

### CTA timing test
Before high-commitment action ask what the user knows, what they must believe, which objections remain, whether commitment matches readiness, and whether a lower-commitment path is useful.

Repeated CTAs are justified when new evidence/readiness moments occur, not as shouting.

Primary conversion should not depend on optional experimental interaction unless completing that interaction is itself the product/action.

## 25. CHOICE / COMPARISON ARCHITECTURE

When users choose among options, resolve decision criteria, meaningful differences, tradeoffs, required information, terminology, and whether options are actually distinct.

Improve grouping, comparison, defaults, recommendation logic, terminology, and progressive disclosure rather than arbitrarily deleting legitimate options.

When comparison is central, place comparable dimensions in a common structure rather than forcing memory across pages.

## 26. ARCHETYPE SPECIALIZATION

### Ecommerce
Resolve catalog mental model, category structure, filtering, comparison, PDP decision criteria, shipping/returns, pricing/offers, checkout friction, confidence information.

### B2B / High Consideration
Emphasize category clarity, buyer outcome, mechanism, use cases, implementation, scale, integration, risk, proof, and buying process. Support relevant evaluator/technical/economic/procurement roles without persona bureaucracy.

### Luxury / Hospitality
Allow desire, place, atmosphere, provenance, materiality, rarity, editorial storytelling, but preserve what is offered, context/location, options, availability/action, trust, practical constraints.

### Portfolio / Agency
Enable judgment of work type, quality, relevance, capability, taste, outcomes/process, contact. Experimental framing may demonstrate capability but must not obscure the work.

### Editorial / Research
Prioritize hierarchy, summaries, chapter structure, scannable headings, progressive depth, attribution, navigation. Structure depth rather than deleting it.

### Public Service / Utility
Prioritize user task, plain language, requirements, next steps, recovery/help. Brand narrative is subordinate to task completion unless it materially supports trust/comprehension.

## 27. COPY ARCHITECTURE

Five levels:
- COPY-1 PAGE PROMISE
- COPY-2 SECTION CLAIMS
- COPY-3 SUPPORTING EXPLANATION
- COPY-4 EVIDENCE
- COPY-5 ACTION LANGUAGE

### Headline responsibility
A headline should orient, state value, identify topic, establish difference, frame a decision, or transition narrative. Creative language is acceptable when nearby context preserves meaning.

### Headings-only test
Read only title, H1, section headings, CTA labels. Can a qualified user roughly reconstruct the page's topic, offer, progression, and next steps?

### Section copy order
1. Core message
2. Supporting explanation
3. Proof/detail
4. Action if relevant

Front-load meaning when comprehension is primary.

## 28. SCANNABILITY / DENSITY / LANGUAGE

Support scanning through descriptive headings, information-carrying openings, meaningful links, conceptual units, real lists, summaries, numbers where meaningful, and consistent structures.

Scannability means retrievable meaning, not aggressively short copy.

Copy density depends on information complexity, expertise, stakes, page role, evidence needs, and differentiation. There is no universal ideal word count.

Prefer language the audience understands. Avoid internal jargon, unexplained acronyms, vague abstractions, bloated corporate syntax, and promotional adjectives substituting for evidence.

Distinctive voice and information density can coexist.

## 29. SPECIFICITY / CLAIM STRENGTH

Prefer concrete nouns, actual mechanisms, real outcomes, named users, quantities, timeframes, constraints, examples.

Use numbers only when accurate, meaningful, contextualized.

Claim strength must match evidence strength.

## 30. DIFFERENTIATION

Evaluate each differentiator:
- Is it true?
- Distinct?
- Relevant?
- Provable?
- Does it alter the user's decision?

Do not create a generic Why Us section by default. Place differences and proof where they support decisions.

## 31. TRUST ARCHITECTURE

Trust emerges from factual specificity, verifiable claims, credible proof, appropriate professionalism, transparency, clear policies, realistic language, working functionality, appropriate design quality, and organizational legitimacy.

Match trust architecture to Strategy Vector Trust Burden.

## 32. NARRATIVE TRANSITIONS

Each major section should answer the question created by the previous section or introduce the next necessary question.

Example:
`claim -> how? -> mechanism -> does it work? -> proof -> will it fit me? -> fit/implementation -> action`

## 33. PAGE LENGTH

No universal ideal. Too long when redundant, irrelevant, or action becomes harder to find. Too short when critical questions/proof/fit/risk remain unresolved.

Judge information utility, not scroll distance alone.

## 34. FIRST-SCREEN STRATEGY

Determine which are required immediately:
- category
- audience
- outcome
- offer
- differentiation
- CTA
- trust cue

Not every project needs all seven.

### First-screen scent test
Can a qualified first-time user determine general category, likely relevance, and what they can do next? If not, delayed clarity must be intentionally justified and repaid.

## 35. CONTENT PRIORITY MATRIX

Use as a discussion aid, not mathematical truth:
- User Necessity 0–2
- Decision Impact 0–2
- Frequency/Relevance 0–2
- Trust/Risk Impact 0–2

Higher priority generally deserves earlier or more prominent information structure.

## 36. CONTENT GAP REGISTER

```text
CONTENT REQUIRED:
WHY REQUIRED:
CURRENT STATUS:
OWNER/SOURCE:
BLOCKS DESIGN? YES/NO
```

Do not conceal strategic content gaps with visual design.

## 37. CONDITIONAL RULES

- Embed proof near material claims.
- Progressively conventionalize when expressive discovery becomes precise task completion.
- Higher commitment requires greater decision support.
- Optional experience must not block essential action.
- Front-load the gist when rapid comprehension matters.
- Maintain high information scent on critical paths.
- Show differences where the user decides.

## 38. STRUCTURAL PATTERNS

Optional, not doctrine:

**Outcome-led platform** — Outcome → capability families → proof → buyer contexts → implementation → action.

**Operational workflow** — Problem/context → workflow stages → solution mapping → outcomes → proof → action.

**High-consideration decision ramp** — Relevance → value → mechanism → proof → fit → risk → action.

**Product discovery** — Category → browse/filter → compare → evaluate → confidence → transaction.

**Experience to utility** — Atmosphere/context → exploration → specific offer/content → practical evaluation → action.

**Editorial depth** — Summary → chapter choices → analysis → evidence/data → deeper reference.

## 39. FAILURE MODES

- Template-first architecture
- Internal-org IA
- Feature laundry
- Proof graveyard
- CTA spam
- Market-speak
- Copy outruns proof
- Clever-but-opaque headings
- False simplicity
- One-funnel myth
- FAQ as architecture repair
- Brand story before relevance
- Unqualified minimalism
- Overexplanation

PASS only when:
- audience, user job, business objective, user decision, and primary action are known;
- offer/outcome/mechanism are sufficiently clear;
- IA/navigation logic exists;
- required beliefs and causal narrative exist;
- critical claims have proof or are reduced/flagged;
- CTA hierarchy matches commitment/readiness;
- copy hierarchy and labels are meaningful;
- `PROJECT_WEBSITE_SPEC` is updated.

## 45. RED TEAM

Ask:
- Are we describing real user decisions or company positioning?
- Did we invent buyer pain?
- Does taxonomy match user thinking?
- Is the page a familiar template rather than a causal sequence?
- Which claims are unsupported?
- Are CTAs requesting commitment too early?
- Could a competitor use the same copy unchanged?
- Are limitations hidden?
- Is choice architecture manipulative?

## 46. SUCCESS STANDARD

This module succeeds when visual design no longer needs to invent the audience, offer, hierarchy, narrative, proof logic, conversion logic, CTA hierarchy, section purpose, or essential copy structure.
